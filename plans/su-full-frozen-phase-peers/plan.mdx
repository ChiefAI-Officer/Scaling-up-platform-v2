# Scaling Up Full: Frozen Phase Peers

<Callout tone="warning">
  **Not deployed.** This is a local architecture talking guide, not a live product
  preview and not something a respondent can test. It does not authorize a push,
  PR, publication, deployment, feature activation, production mutation, or external
  communication.
</Callout>

## The decision in one sentence

Select Peers from an explicit five-phase catalogue **when the assessment is scored**,
freeze all 61 selected values and their provenance into the result, and render only
that frozen snapshot.

<Callout tone="decision">
  The hard-to-reverse architecture bet is intentionally small: use the immutable
  assessment-version JSON and the already persisted score result. Do not introduce a
  new benchmark-snapshot database subsystem.
</Callout>

### Why freeze the values?

- A report means the same thing tomorrow as it did when scored.
- Changing an admin benchmark row cannot silently rewrite a historical report.
- On-screen, PDF, and revived-session views consume one source of truth.
- The selected phase and catalogue edition are auditable without reconstructing state.

## Failure behavior

<Callout tone="warning">
  Missing P4 must never mean “use baseline.” Phase-aware data is all-or-nothing.
</Callout>

| Boundary | Failure behavior |
| --- | --- |
| Draft/publish validation | Reject missing/duplicate phases, incomplete keys, invalid values, unresolved references, or hash mismatch |
| Scoring | Fail closed if the exact frozen phase cannot resolve all 61 peer values |
| Rendering a declared frozen result | If corrupt/incomplete, omit Peers and emit a structured diagnostic; never query mutable rows or substitute baseline |
| Rendering a genuinely historical result | Use the explicit legacy baseline constant and record legacy-fallback telemetry |

## Report wording

> **Peers** are a governed benchmark snapshot selected by organizational phase and
> frozen when this result was scored. This is not an industry-, geography-, or
> cohort-matched comparison.

This replaces the inaccurate implication that one current mutable reference is good
for every phase. It also avoids overstating what the Esperto evidence proves.

### Required implementation proof

- P1–P5 exact-vector and completeness tests.
- P3 → P4 56-change proof and P4 → P5 56-reversion proof.
- Same-phase score invariance.
- Frozen serialization and session-revival parity.
- Mutable-row tamper test: new reports cannot change.
- Legacy immutability and no-backfill proof.
- Corrupt snapshot fail-closed behavior.
- On-screen/PDF agreement and stable 26-page report shape.
- LVA regression coverage.
- Changed-file ESLint, targeted Jest, migration safety, and Turbopack build gate before any push.

## Alternatives rejected

| Alternative | Why it was rejected |
| --- | --- |
| New database snapshot subsystem | Adds schema, lifecycle, and migration complexity when immutable version JSON plus the score result already provide the right boundaries |
| Resolve peers from headcount at render time | Makes reports mutable, duplicates phase logic, and can disagree with the phase frozen during scoring |
| Keep using current `AssessmentBenchmark` rows | Cannot represent the proven phase split safely and lets later edits reinterpret historical reports |
| Default every unmapped phase to baseline | Would hide a missing P4 mapping—the most important observed exception |
| Rewrite historical results | Changes historical meaning and requires unnecessary high-risk production mutation |

## Review focus

Please review these three points before implementation planning:

1. Does the distinction between **You**, **Feedback**, and **Peers** match how you want
   the report explained?
2. Is the forward-only legacy treatment acceptable: old results remain baseline and
   are not upgraded to phase-aware Peers?
3. Is the proposed disclosure precise enough without overstating the benchmark?
