# ADR-0026 — Participant Welcome-screen copy is code-owned per template alias, not a Template row column

**Status:** Superseded by [ADR-0033](0033-admin-owned-invited-welcome-snapshots.md) (2026-08-10). Accepted on 2026-07-28 and first implemented for the Jeff July-10 welcome-lede family (#62 LVA, #66 QSP v2, #70 Rockefeller, #77 SU-Full) as [welcome-copy.ts](../../src/src/lib/assessments/welcome-copy.ts).

## Context

The invited participant surface opens on a **Welcome screen** — Screen 1 of `/org-survey/[campaignAlias]`, before the Section pager — and its lede paragraph was a **hardcoded JSX string**: one string shared by every invited template, zero per-template branching ([org-survey-client.tsx](../../src/src/components/assessments/org-survey-client.tsx)). Jeff's July-10 tracker asks for instrument-specific wording on four of the six invited instruments.

The paragraph was not data in any sense: a repo-wide grep finds it only in the JSX (now `welcome-copy.ts`), and a 2026-07-28 production query found no row whose `AssessmentCampaign.description`, `AssessmentTemplate.description`, or Template Version JSON contained it. (Those `description` columns are populated — with admin-facing blurbs, not this paragraph.) Meanwhile `AssessmentCampaign.description` — the field that looks like its home — is plumbed but **dead on the invited surface**, rendering only on the public quiz ([public-quiz-client.tsx](../../src/src/components/assessments/public-quiz-client.tsx)).

The obvious move is to put it on `AssessmentTemplate` beside the invitation copy. **ADR-0025 is the reason not to.** Invitation copy is data on the template row because coaches *author* it — the per-campaign override is a first-class writable path — and that has been paid for since: a template column, a seed that is only a factory default, four atomic compare-and-swap patch scripts to correct live rows, a shared coverage receipt, seed↔script drift guards, stale version `contentHash`es, and a live precedence bypass where a campaign-level override silently shields a campaign from every template-level correction (GH #220 — the proven root cause of Jeff's QSP invitation report). Welcome-screen copy has **none** of the drivers that justified that cost: nobody has asked to author it per campaign, it is not per-recipient, it carries no merge variables, and it changes about as often as a renderer does.

There is already a shape for exactly this in the assessments module, used twice. [report-config.ts](../../src/src/lib/assessments/report-config.ts) keys per-template presentation policy off `AssessmentTemplate.alias` with a documented fail-open default and the standing note that *"Report TYPE is a global presentation policy (intentionally retroactive); report CONTENT stays version-pinned"* (ADR-0010). `ORG_LINE_SUPPRESSED_ALIASES` / `shouldShowOrgLine()` is the same shape again for invitation-header chrome, down to the "unknown/null alias → prior output" fail-open ([invitation-email.ts](../../src/src/lib/assessments/invitation-email.ts)) — and it shipped with no ADR, which is part of why this one is written.

## Decision

**Participant Welcome-screen lede copy is CODE-OWNED, in a per-alias map keyed by `AssessmentTemplate.alias`** — not a Template row column, not a Template Version field, not per-campaign content.

- **One pure module.** `welcome-copy.ts` exports `DEFAULT_WELCOME_LEDE`, `RESUME_NOTE`, `WELCOME_LEDE_BY_ALIAS`, `resolveWelcomeLede(alias)` and `shouldShowResumeNote(alias)`. No Prisma, no React, no I/O.
- **Values are `readonly string[]` — paragraphs, not one blob.** The array *is* the paragraph split; the render site emits one `<p className="su-welcome-lede">` per element. Authors do not embed newlines and the renderer does not parse them.
- **Fail-open to the default.** Unknown alias, `null`, `undefined` or `""` resolve to `DEFAULT_WELCOME_LEDE`, byte-identical to the paragraph that shipped before this existed and pinned by an exact-string test with a length tripwire. Adding a template is safe by construction.
- **Five aliases carry bespoke copy** — `leadership-vision-alignment`, `qsp-v2`, `RockHabits`, `scaling-up-full` (Jeff's dictated copy) and `five-dysfunctions` (drafted by us, flagged to him as such, because leaving one instrument on generic copy while its four siblings describe themselves was the worse option). `qsp-v1` keeps the default. `scaling-up-quick` is out of scope *by convention*, not by constraint: every campaign on it is PUBLIC today, so it renders a different component. If an INVITED campaign is ever created on it, it fails open to the default lede.
- **`resolveWelcomeLede()` is the seam.** The resolver is where the lookup *policy* lives, so promoting this to data is a bounded change rather than a rewrite: the map becomes a data read, `shouldShowResumeNote` takes the same input, and the render site threads one extra value in from `/me`. Be precise about the limit, though — the resolver is called **synchronously inside a `"use client"` render body**, so a DB read cannot simply hide behind today's signature; the value has to arrive on the `/me` payload. What survives untouched is the paragraph contract and the default's byte-pin.
- **Asymmetric with ADR-0025, deliberately.** Invitation copy is data *because it is coach-authored*; Welcome copy is code *because it is not*. The discriminator is **authorship**, not surface or subject matter. A future reader should apply that test rather than assume "participant-facing copy lives together."
- **Flagless, no migration, no prod write, no seed edit.** The map is its own kill switch (delete an entry, redeploy). Rollback is a revert, per the ADR-0010 precedent that pure rendering does not earn a flag.

## Consequences

**Positive**

- Editing a paragraph is a one-line diff in a unit-tested pure module, reviewed like code — no migration, no editor field, no CAS patch script, no coverage receipt, no seed↔row drift guard.
- Immune to the GH #220 class of bug: there is no override layer above this copy, so what the map says is what every campaign renders. A copy fix cannot silently miss a campaign.
- Version `contentHash`es are untouched, so this cannot add to the seeder-hygiene debt ADR-0025 documents (today `RockHabits` v3 and `leadership-vision-alignment` v4 already fail a re-seed closed).

**Negative / accepted trade-offs**

- **Retroactive, and more aggressively so than report policy.** The Welcome screen is re-derived on *every* mount: on initial load once `/me` resolves, and again whenever a respondent backs out of the pager, which sets `phase` straight back to `intro` (see the `/me` effect and `onExit` in [org-survey-client.tsx](../../src/src/components/assessments/org-survey-client.tsx), both calling `setPhase({ kind: "intro" })`). There is no snapshot and nothing version-pinned. A deploy therefore changes the wording of campaigns already in flight, and a respondent who starts, leaves, resumes and taps Back can read a *different* paragraph than the one they started with, within one sitting. Accepted: the lede is unscored, bears no answer, and is not consent or instructions a submission is evaluated against. **If a future item makes Screen 1 answer-bearing — a consent checkbox, an attestation — revisit this before it ships;** retroactive copy under a signature is a different question.
- **Invited surface only.** `accessMode` is per-**campaign**, not per-template — the public route admits a campaign only when `accessMode === "PUBLIC"` ([quiz page](../../src/src/app/(public)/quiz/[campaignAlias]/page.tsx)). A PUBLIC campaign created on a keyed template would render `public-quiz-client.tsx` (campaign description, else the Four-Decisions fallback) and would **not** show this copy. As of 2026-07-28 every keyed template is invited-only in production, so the gap is theoretical — an observation with a date, not a constraint. When it stops being theoretical, the fix is to call `resolveWelcomeLede()` from the public component as its *fallback* branch — replacing the hardcoded Four-Decisions string while `campaign.description` keeps precedence — **not** to duplicate the copy into a second map.
- **Changing copy requires a deploy.** No coach or admin can edit it; there is no field, and adding one is the rejected alternative below. A request to edit it live is a promotion decision, not a bug.
- **A representation split to reconcile if it is ever promoted.** The invited surface renders paragraphs as sibling `<p>` elements; the public quiz renders multi-paragraph text as **one** `<p>` with `whiteSpace: "pre-line"` ([public-quiz-client.tsx](../../src/src/components/assessments/public-quiz-client.tsx)). A `readonly string[]` and a newline-delimited string are not the same contract. Unify at the promotion, not by quietly teaching one surface to parse the other's format.

## Alternatives considered

- **A new `AssessmentTemplate` column (e.g. `welcomeLede`) edited in the template editor** — rejected. Per ADR-0025's actual experience that column is not one change: a migration, an editor field with validation, a seed edit that is only a factory default, an atomic compare-and-swap script to correct the live row (a deploy never rewrites row data), a seed↔script parity guard plus a drift guard, and a coverage receipt to prove which campaigns the patch reached. It also *inherits* the GH #220 campaign-override bypass the moment anyone adds an override — the exact failure mode that made Jeff's QSP invitation look like a regression when it was not. All of that buys coach authorship, which nobody requested for this paragraph.
- **Per-campaign Wave M Custom slides** (`AssessmentCampaign.customSlides`, [schema.prisma](../../src/prisma/schema.prisma)) — rejected on two independent grounds. It is **campaign-scoped**, so an instrument-level paragraph true of every QSP forever would be re-authored on every new campaign, every quarter, by hand, with drift guaranteed. And it renders in the **wrong place**: custom slides are merged into the pager's page list by `mergeCustomSlides` and displayed by `SectionPager` ([org-survey-client.tsx](../../src/src/components/assessments/org-survey-client.tsx)) — i.e. *after* the respondent presses Start. It cannot be Screen 1.
- **A Template Version field, published per version** — rejected. It would version-pin the copy, but that is the wrong semantics for the same reason report *type* is not version-pinned (ADR-0010): this is presentation policy about the instrument, not content a submission is scored against. It would also mean a DRAFT→publish cycle per typo, on templates whose latest version is already an unpublished draft.
- **The map plus a feature flag** — rejected, matching ADR-0010: pure rendering with no external side effect, the map is already the kill switch, and a flag adds ceremony plus (per the 2026-07-22 audit) a durable way for the feature to be silently off in production.
