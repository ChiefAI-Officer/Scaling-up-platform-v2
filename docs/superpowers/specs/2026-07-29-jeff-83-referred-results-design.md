# Jeff #83 — Public Referred Results Design

**Status:** Approved in `grill-with-docs` session on 2026-07-29

**Scope:** Finish the partially shipped Jeff item #83

**Related:** PR #205, ADR-0008, ADR-0007, ADR-0012, ADR-0028

**Visual review:** [`docs/specs/v7.6/mockups/83-referred-results-scope.html`](../../specs/v7.6/mockups/83-referred-results-scope.html)

## Problem

The public Quick Assessment already:

- accepts a per-coach attributed link;
- resolves the supplied coach reference through the active-coach guard;
- stores the frozen answers and score;
- shows and emails the canonical Results report to the taker;
- emails the same report to a verified referring coach; and
- exposes taker name, email, referring-coach email, and submission date to ADMIN/STAFF on Public Campaigns.

It does not give the referring coach persistent in-app visibility, and the admin surface cannot show what result the taker received. The stored `referringCoachEmail` is also not a safe authorization key: it is a supplied snapshot, can change independently of Coach identity, and is currently stored even when the active-coach guard does not resolve a coach.

## Outcome

Finish #83 by:

1. freezing verified referral ownership to a Coach identity at submission time;
2. adding a dedicated Coach-lane **Referred Results** destination;
3. enriching the existing admin Public Campaigns expander with scores and report access;
4. reusing the canonical Results report behind an authenticated submission-based access gate; and
5. correcting the public privacy disclosure before launch.

This is a read-only visibility feature, not a public-campaign management or CRM feature.

## Approaches considered

### 1. Authorize by current coach email

Query public submissions where normalized `referringCoachEmail` equals the signed-in coach's current email.

This is the smallest schema change, but it is unsafe. Email changes can orphan results; email reuse can transfer named personal data to another person; and historical unverified values are indistinguishable from verified referrals.

### 2. Authorize by Public Campaign ownership

Reuse `canManageCampaign` and show submissions to the campaign creator or Organization owner.

This conflicts with the domain. Public Campaigns are admin-created, while referral ownership belongs to the coach whose attributed link generated the submission. Campaign ownership and referral ownership are deliberately different.

### 3. Freeze verified Coach identity — selected

Store the Coach resolved by the active-coach guard as immutable submission ownership, and check current status separately when serving coach requests.

This cleanly separates:

- **ownership:** who the verified referral belonged to at submission time; and
- **eligibility:** whether that same Coach may view it now.

See ADR-0028.

## Domain model

### Referring coach

The active Coach verified when the public taker submits. The association is submission-scoped and frozen. It is not the Public Campaign creator or Organization owner.

### Referred Results

The dedicated Coach-lane collection of public submissions owned by the signed-in referring Coach. It contains the coach's shareable Quick Assessment link and the read-only results generated by that link.

### Ownership versus eligibility

- The frozen Coach relationship does not change if the Coach edits their email.
- The Coach may view the result only while currently active and unexpired.
- Deactivation or certification expiry suspends access.
- Reactivation of the same Coach restores access.
- ADMIN/STAFF retain oversight.
- A submission without verified Coach ownership is ADMIN/STAFF-only.

## Data design

Add a nullable relation to `AssessmentSubmission`:

```prisma
referringCoachId String?
referringCoach   Coach? @relation("AssessmentSubmissionReferringCoach", fields: [referringCoachId], references: [id], onDelete: Restrict)

@@index([referringCoachId, submittedAt])
```

Add the inverse relation to `Coach`.

Keep `referringCoachEmail` as an immutable delivery/audit snapshot. It is no longer an authorization source.

### New submissions

The public submission path must:

1. normalize the coach reference;
2. resolve a currently active, unexpired Coach;
3. persist `referringCoachId = coach.id` and `referringCoachEmail = coach.email` when verification succeeds;
4. persist both fields as null when verification fails or no referral is present; and
5. enqueue the referring-coach email only for that same verified Coach.

Coach resolution, submission creation, and outbox creation must behave as one logical write. Tests must prove the stored owner and emailed recipient cannot diverge.

This intentionally changes today's behavior, which stores the unverified supplied email even when no active Coach resolves.

### Historical backfill

Backfill only when all of the following agree:

- the submission belongs to a Public Campaign;
- the submission has a `REFERRING_COACH` outbox row;
- the outbox recipient normalizes to one existing Coach email; and
- there is no conflicting referring-coach evidence for that submission.

Use the outbox row because it proves the active-coach guard succeeded at submission time. Do not infer ownership from `AssessmentSubmission.referringCoachEmail` alone.

Production read-only audit on 2026-07-29 found:

- 7 public submissions across 1 campaign;
- 3 submissions with referral emails;
- all 3 have verification outbox evidence;
- all 3 still match existing Coach records; and
- those 3 submissions belong to 2 Coaches.

Ambiguous or unmatched historical records remain `referringCoachId = null`.

### Coach deletion

Hard deletion is blocked when any public submission references the Coach. The existing coach-delete endpoint returns a conflict with direction to deactivate the Coach instead. Assessment history must not disappear or silently lose ownership as a side effect of coach deletion.

Privacy-driven deletion of taker data is separate and out of scope.

## Authorization and report access

Add one pure access policy for a public submission:

- ADMIN/STAFF: allowed.
- COACH: allowed only when:
  - `actor.coachId` equals the frozen `referringCoachId`;
  - the Coach currently has active, unexpired certification; and
  - the submission belongs to a non-deleted Public Campaign.
- everyone else: denied.

Add an authenticated submission-based report route, provisionally:

```text
/assessments/public-submissions/[submissionId]/report
```

The route:

- resolves the actor;
- rate-limits fail-closed;
- applies the public-submission access policy;
- returns the same not-found response for missing and unauthorized IDs;
- loads the frozen submission result and answers;
- builds the existing `RespondentReport`;
- renders the existing `BrandedReport` and print action;
- disables caching for named personal data; and
- audits every successful and denied report-view attempt through the existing report-gate conventions.

Do not add a bearer-token, public, or emailed results URL for coach access.

## Coach experience

Add **Referred Results** to the Coach lane:

```text
My Campaigns
Referred Results
Members
```

Route, provisionally:

```text
/portal/assessments/referred-results
```

Move the existing **Your Quick Assessment link** card from My Campaigns to this page. Do not duplicate it.

The page is a flat, newest-first collection across all Public Campaigns. It includes:

- taker name and email;
- assessment name;
- overall score and scoring tier, where configured;
- a compact Four Decisions color strip;
- submitted date/time;
- an explicit Details control that expands the domain breakdown;
- View report;
- server-side pagination, 25 per page;
- search by normalized taker name or email; and
- assessment filter.

The page must have:

- loading state;
- an empty state explaining that results appear after someone submits through the coach's link;
- a no-search-results state;
- enumeration-safe error handling;
- mobile card layout below the table breakpoint; and
- accessible controls and keyboard focus.

The page is read-only. It cannot edit answers, delete or reassign submissions, manage the Public Campaign, add notes, change lead status, or trigger CRM workflows.

## ADMIN/STAFF experience

Keep the existing Public Campaigns page and lazy submissions expander. Enrich each submission with:

- verified referring-coach name and email, or “Scaling Up only” when none;
- overall score and tier;
- compact Four Decisions result strip;
- explicit Details expansion for the domain breakdown; and
- authenticated View report.

Do not add a second admin results page.

The existing admin endpoint should adopt bounded server pagination rather than the current unpaged first-100 response.

## API shape

Exact names may change during planning, but the design requires:

### Coach collection

```text
GET /api/assessments/referred-results
  ?cursor=<opaque>
  &query=<name-or-email>
  &templateId=<id>
```

Returns only rows owned by the signed-in active Coach. The response carries display-ready result summaries, never raw answers.

### Admin campaign submissions

Extend:

```text
GET /api/admin/public-campaigns/[id]/submissions
```

with bounded pagination, verified Coach display data, and result summary. ADMIN/STAFF only.

### Full report

The full report is server-rendered through the authenticated report route, not returned from either collection API.

## Privacy and consent

Launch is blocked until the public pre-submit disclosure:

- states that the taker receives the report on screen and by email;
- states that Scaling Up receives the result;
- states that a verified referring coach receives and can later access the full report while active; and
- links to `https://scalingup.com/privacy-policy/`.

The official policy uses purpose-based retention rather than a fixed duration. Product/legal approval is required for final copy; the implementation must not invent a retention period or broader legal claim.

Candidate direction, not approved legal copy:

> Your full report will be shown and emailed to you. It will also be shared with the Scaling Up team and, if you used a coach referral link, made available to that verified coach while their account remains active. Scaling Up retains personal data as described in its Privacy Policy.

The existing taker, referring-coach, and Scaling Up emails remain unchanged.

## Rollout

Use one wave flag and kill switch, provisionally:

```text
WAVE_83_REFERRED_RESULTS_ENABLED
WAVE_83_REFERRED_RESULTS_KILL
```

Flag OFF preserves current navigation, admin result display, report access, and public copy. The nullable schema addition and verified-owner write may safely exist before UI launch, but no new result-reading surface is reachable until the flag is enabled.

Recommended delivery slices:

1. **Ownership foundation:** migration, relation, verified write path, historical backfill, coach-delete guard, access policy.
2. **Canonical report access:** public-submission report loader, gate, route, audit, no-cache behavior.
3. **Coach Referred Results:** navigation, moved link card, collection API, filters, pagination, responsive UI.
4. **Admin completion + privacy:** enrich existing expander, approved disclosure copy, flag launch and production smoke.

Each slice remains behind the same wave flag and should be independently testable.

## Testing and verification

### Data and write path

- Verified active Coach stores canonical ID and email.
- Missing, malformed, unknown, inactive, or expired Coach stores no ownership and sends no coach email.
- Submission owner and outbox recipient cannot diverge.
- Migration backfills only verification-evidenced rows and is idempotent.
- Coach hard deletion is blocked when referrals exist.

### Authorization

- Owning active Coach can list and view only their submissions.
- Another Coach receives enumeration-safe not-found.
- Inactive or expired owner loses list and report access.
- Reactivation restores access.
- ADMIN/STAFF can view referred and unreferred public submissions.
- Unauthenticated access redirects or returns 401 according to page/API convention.
- Soft-deleted campaigns do not expose reports.

### UI

- Link card appears only on Referred Results when the flag is on.
- Newest-first pagination, search, and assessment filter are server-backed.
- Result summary and expanded Four Decisions values come from the frozen result.
- View report renders the canonical report and print action.
- Empty, loading, no-results, error, responsive, and keyboard states are covered.
- Flag OFF is byte-identical on existing UI surfaces.

### Privacy and operations

- Approved consent copy and privacy-policy link render before submission.
- Named report pages send no-store cache headers.
- Report views produce audit records without logging raw answers or taker PII in application logs.

### Required gates

From `src/`:

```bash
npx eslint <changed files>
npx jest <targeted suites> --runInBand
node scripts/check-migration-safety.mjs
CI=true npx next build --turbopack
```

The current `quick-assessment-submit.test.ts` baseline has a pre-existing stale mock: campaign fixtures omit `deletedAt`, causing 17 false 404 failures on current `main`. Repair that fixture in the ownership-foundation slice before using the suite as a release gate; do not misattribute those failures to #83.

## Out of scope

- CRM or HubSpot integration.
- Lead stages, notes, tasks, assignments, or contact workflows.
- Editing answers or recomputing frozen scores.
- Reassigning referral ownership.
- Deleting submissions through Referred Results.
- Managing the Public Campaign from the coach page.
- Raw-answer JSON views.
- Public or reusable tokenized coach report links.
- A reduced or coach-specific report format.
- A second admin-wide results destination.
